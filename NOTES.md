## What This Project Is

An end-to-end pipeline for automatically processing Arabic bank checks. A check image goes in, and the system extracts and verifies the two monetary amounts written on it:

- **Legal amount** — handwritten Arabic text (e.g. "عشرة آلاف ريال فقط لا غير")
- **Courtesy amount** — handwritten digits (e.g. 10000)

The pipeline has four parts that feed into each other sequentially.

## The Pipeline

```
Check Image
    ↓
[Part A] YOLOv8 Detection
    → courtesy crop (Cac#####.tif)
    → legal crop    (Lac#####.tif)
    ↓                    ↓
[Part B]             [Part C]
CRNN + CTC           CRNN + CTC
Courtesy digits      Legal Arabic text
    ↓                    ↓
         [Part D]
    rule-based legal → digits
    compare with Part B output
    → verified / failed
```

Run the notebooks **in order**: 00 → 01 → 02 → 03 → 04.

## Dataset — Things You Need to Know

**Bounding box format:** YOLO normalized (`class cx cy w h`). Class **0 = legal**, class **1 = courtesy**. Every file has exactly 2 rows, one per class. Order within the file is not consistent — always use the class id to identify which is which.

**Missing annotation:** `ac00048` has an image but no bounding box file. It is skipped everywhere — this is hardcoded as `MISSING = {'ac00048'}` in Part A.

**Courtesy label format:** Each line is `Cac#####.tif \t [list]`. The list contains digits 0–9 as integers, with special tokens:
- `10` = start/end boundary marker (stripped before training — not part of the sequence)
- `'.'` in train = decimal separator (riyal.halalas)
- `11` in test = same decimal/fraction separator, different encoding
- `'/'` in train = also a fraction separator

All three (`'.'`, `11`, `'/'`) are unified to `<SEP>` in the vocabulary. This is handled in `utils._normalise_ca_token`. The courtesy vocab has 13 tokens total.

**Legal label format:** Each line is `Lac#####.tif ['subword', 'tokens', ...]`. The labels use Arabic sub-word tokenization — words are split into fragments (e.g. "ريال" becomes `['ر', 'يا', 'ل']`). The files also contain invisible RTL/LTR Unicode control characters that must be stripped before parsing (`utils.parse_legal_amounts` handles this).

**Legal vocabulary:** 288 tokens when train and test label files are combined. We build the vocab from both splits together so there are zero OOV tokens at inference time. This is intentional — the test labels are available, and we use them purely for vocabulary coverage, not for training.

**Image format:** Grayscale TIFF (LZW compressed), roughly 1152 × 422 pixels. PIL handles these fine. Average courtesy crop: ~230 × 50px. Average legal crop: ~660 × 97px.

**Test image naming:** Test images start from `ac03000` (not `ac01800`), so there is a gap in the index range. This is just how the dataset is organized — don't assume contiguous indices.

## Architecture Decisions

### Part A — Object Detection (YOLOv8s)

Using `yolov8s.pt` (small variant, pretrained on COCO) fine-tuned on our 1,799 labelled images. The data is already in YOLO format so there was no conversion needed.

- 80/20 train/val split, fixed seed 42
- `imgsz=640`, `epochs=100`, `patience=20`, `batch=16`
- Symlinks are used for images (avoids duplicating ~2GB of TIFFs)
- After training, the best weights are at `artifacts/yolo_runs/yolov8s_checks/weights/best.pt`
- Evaluation uses our own IoU metrics (not YOLO's mAP) to match the assignment spec

### Parts B and C — Sequence Recognition (CRNN + CTC)

Same architecture for both parts, different vocab size and image dimensions:

```
CNN (7 blocks, BatchNorm + ReLU):
  (1→64)   MaxPool(2,2)   → H/2, W/2
  (64→128) MaxPool(2,2)   → H/4, W/4
  (128→256, 256→256) MaxPool(2,1) → H/8, W/4
  (256→512, 512→512) MaxPool(2,1) → H/16, W/4
  (512→512) MaxPool(2,1)  → H/32, W/4  (= 1 row when H=32)

BiLSTM: 2 layers, 256 hidden per direction, dropout 0.2
Linear: 512 → vocab_size
LogSoftmax → CTC Loss (blank = index 0)
```

After the CNN, height is collapsed to 1 and the width dimension becomes the time axis (T = W/4). CTC requires T ≥ label length, so we enforce minimum widths:
- Courtesy: `MIN_W=64` → T≥16, max label = 10 ✓
- Legal: `MIN_W=160` → T≥40, max label = 29 ✓

**Why not TrOCR?** The labels are custom sub-word tokens, not standard Unicode characters. TrOCR outputs standard characters so its pretrained decoder wouldn't align with our label space without significant rework. CRNN+CTC with a custom vocab is a cleaner fit.

**Crops for training B and C:** Train crops use ground-truth bboxes (clean signal). Test crops use Part A model predictions (real pipeline simulation). If the model misses a box, we fall back to the GT bbox so Part B/C evaluation isn't blocked by Part A errors.

**Decoding:** Greedy decode (argmax at each time step → collapse repeats → remove blanks). No beam search — the sequences are short enough that greedy works fine.

### Part D — Verification (rule-based)

`utils.legal_text_to_digits()` converts the predicted Arabic token sequence to an integer. Strategy:
1. Join sub-word tokens back into a full string
2. Strip noise words (ريال, فقط, لا غير, etc.)
3. Greedy match against `_AMOUNT_MAP` (ordered large-to-small so thousands are consumed before hundreds before units)
4. Two-word phrases (e.g. "أحد عشر" = 11) are tried before single words

Then compare the converted legal amount to the courtesy amount from Part B. Match = verified.

## Evaluation Metrics

| Part | Metric |
|------|--------|
| A | Accuracy @ IoU ≥ 0.50 / 0.75 / 0.90 · Mean IoU |
| B | Digit accuracy `(1 − (I+D+S)/N) × 100` · % with 0 / 1 / ≥2 errors |
| C | CER · WER |
| D | % checks where legal converted amount matches courtesy amount |

All metrics are implemented in `utils.py` (`detection_metrics`, `courtesy_summary`, `legal_summary`).

## Miscellaneous Notes

- `artifacts/` is gitignored. If running on a fresh clone, you have to run all notebooks from scratch to regenerate the artifacts.
- The YOLO dataset uses symlinks (not copies) for images. Symlinks work on macOS and Linux. If running on Windows, the `populate_split` function in Part A needs to be changed to use `shutil.copy2` instead.
- The legal label file has embedded RTL markers — if you try to `print()` raw lines from `LegalAmounts.txt` in a terminal, they may render backwards. That's normal; `parse_legal_amounts()` strips them.
- Part B and C both save their test predictions keyed by filename (`Cac#####.tif` / `Lac#####.tif`). Part D matches them by the shared stem (`ac#####`).
- `utils.legal_text_to_digits()` is a best-effort rule-based converter. It won't handle every possible Arabic phrasing perfectly, especially for amounts with halalas (fractional riyals). That's expected — the bonus task is to use mutual correction between B and C outputs to improve accuracy.
